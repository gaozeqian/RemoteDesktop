# 安全说明

这份文档说明这套软件保护什么、怎么保护、以及**还没有保护什么**。前半部分是代码里已经实现并测试过的机制，
后半部分是使用者和部署者必须自己承担的边界。写这份文档的目的不是让人放心，而是让人知道该在哪里设防。

## 谁在防谁

被控端（本机）默认是"关着"的：要连上来必须知道设备代码和密码。连接建好之后，控制端能做什么由被控端逐项授予，
而且**授予和收回都由被控端执行**，不依赖控制端界面是否配合。

要防的主要是这几类人：

| 对手 | 他能做什么 | 靠什么挡住 |
|---|---|---|
| 网络上的陌生人 | 扫描端口、往被控端发连接、猜密码 | QUIC + TLS 1.3、证书指纹固定、密码证明、失败限流、握手并发上限 |
| 中转服务器（或劫持服务器的人） | 转发流量、看到谁连谁 | 端到端加密（中转只转发密文）、中继票据只由 Rendezvous 签发 |
| 信令服务器（或劫持服务器的人） | 看到谁在关注哪些设备代码（在线状态查询）、谎报在线或离线 | 查询按设备限流；答案只是所问代码的子集；状态灯不参与任何权限判断，连接仍以实际握手结果为准；可用 `Rendezvous:PresenceEnabled=false` 关掉 |
| 已授权但意图越界的控制端 | 试图绕过权限、看登录界面时的磁盘、读别人的文件 | 被控端逐通道授权、观看模式在被控端强制、文件和终端只能以登录用户身份运行 |
| 被控端本机的其他程序 | 读取设备身份、改摄像头开关 | 密钥用 DPAPI 加密 + 目录 ACL、命名管道 ACL |

## 连接与身份

- **传输**：QUIC（TLS 1.3）。双方在自己这边**固定对端证书指纹**，指纹通过 Rendezvous 信令交换，所以中间人拿不到
  一个双方都接受的证书。中转服务器只看到密文。
- **设备身份**：每台设备第一次启动生成密钥与自签证书，设备代码由服务器分配。私钥用 DPAPI 加密存放
  （服务用 `LocalMachine` 作用域、放在只允许 SYSTEM 和管理员访问的目录；客户端用 `CurrentUser`）。
- **密码**：临时密码（可刷新）或可选的固定密码。密码**从不明文传输**，控制端发的是
  `HMAC(PBKDF2(密码, salt = nonce), nonce ‖ 双方证书指纹)`，绑定到这一次连接的双方证书，换一条连接重放无效。
  口令先经 60 万轮 PBKDF2 才成为密钥，且每次连接的 nonce 就是盐——这两件事都是给"拿到证明后离线猜口令"的人
  加价的（见下面 PAKE 那一条：加价不等于解决）。
- **临时密码会自己过期**：30 分钟（`HostCredentials.TemporaryPasswordLifetime`）之后，下一次有人看它就被换掉。
  它是给人念出来、可能被拍照或粘进聊天窗的那一个，不该长期有效。**固定密码不过期**——长期有效正是它存在的理由。
- **中继绑定要证明"收得到"**：中继收到绑定请求后，先往来源地址发一个令牌，只有带着这个令牌回来的绑定才会生效
  （`RelayCookie`）。令牌与票据、角色、来源地址和时间窗绑定。没有这一步，任何拿到票据的人都能把中继指向一个
  别人的地址，让那些 UDP 包以中继的身份到达——一份隐藏来源的发包工具。
- **猜密码**：同一控制端设备 5 分钟内失败 5 次即锁定；全局 1 分钟内失败 20 次锁所有人一分钟（防换着设备试探）。
  失败会记日志（含控制端设备代码）。
- **半开连接洪泛**：被控端同时只允许 32 个连接处于握手阶段，超出的连接直接丢弃（洪泛者付出一次往返，被控端几乎不付出代价）。
  已建好的会话不受影响，因为配额只覆盖握手。

## 信令服务器自己的暴露面

服务器是唯一一个"谁都连得上"的组件，所以它自己也要有账算。下面的限额都是默认开着的
（完整清单和调法见 [deployment.md](deployment.md) 的"公网上的限额"）：

- **同时服务的设备数**有上限，超出的连接在 WebSocket 升级**之前**就被拒绝——洪泛者付出一次往返，服务器不留内存。
  单个来源地址另有更低的上限，一台机器占不满整个服务器。
- **注册要花配额**：注册就是领一个身份，而这台服务器上其它所有限额都是按身份计的（在线状态查询、连接请求）。
  没有这条，脚本可以无限注册身份，把"每设备"的限额摊薄成没有。这是 Sybil 那道闸。
- **连接请求要花配额**，而且一台设备能同时挂起的请求数有上限：否则任何人都能拿它去轰炸某台在线设备的弹窗，
  顺带无限签发中继票据。
- **限流事件会写日志，带来源地址**。这是服务器唯一记录地址的地方，只在拒绝时写，专门留给运维排查滥用。
  正常连接的日志里没有地址。
- **TLS 由部署者打开**（`wss://`）。客户端对信令服务器**不做指纹固定**，依赖系统信任链，所以证书域名要对得上。
  不打开 TLS 的后果见下面"还没有做的事"里 PAKE 那一条——泄露的不只是元数据。

反过来，服务器**看不到**画面、按键、文件和终端内容：那些走两端之间的 QUIC，服务器只经手中继密文。

## 授权（会话里能做什么）

权限在被控端算出来，规则在 `AccessGrant` 里，任何一条通道在被功能模块看到之前先经 `ChannelDispatcher` 授权：

- 控制端请求的权限 ∩ 被控端策略允许的权限。
- **观看模式**强制只读，与请求和策略无关；没有屏幕权限时，输入和剪贴板一并去掉。
- 被控端可以随时把某个会话降级为"仅观看"或收回摄像头：相关通道立刻被取消，控制端只是被通知（界面跟着变），
  执行不依赖它。
- **同时最多 16 个会话**（`HostSessionService.MaxSessions`）。每个会话都要占用这台机器的内存直到断开，而知道密码
  就能走到这一步，所以没有上限时，一个人就能一直开会话直到机器撑不住。平时从手机和笔记本各连一个，
  离这个数还很远。
- 摄像头作为常规远程功能，默认随控制会话开放（`HostPolicy`）；观看模式下强制不开放。

## 各功能模块的边界

| 功能 | 谁能用 | 关键限制 |
|---|---|---|
| 屏幕（视频） | `ViewScreen`（观看模式也有） | 只读；被控端不接收任何输入 |
| 输入 | `ControlInput` | 观看模式下被控端拒绝该通道 |
| 剪贴板 | `Clipboard` | 只同步会话期间的**变化**；观看模式不开放 |
| 音频 | `Audio` | 只送被控端正在播放的声音 |
| 文件 | `FileTransfer` | 以**登录用户**身份执行；路径过 `FileAccessPolicy`；可选根目录限制 |
| 终端 | `Terminal` | 只能选被控端列出的 shell 名字；并发上限 8；shell 随会话结束 |
| 摄像头 | `Camera` | 作为常规功能开放；观看模式不开放；被控端可单会话关停；使用中被控端有提示 |

具体到容易出问题的地方：

- **文件和终端绝不以 SYSTEM 运行**：它们在会话 Agent 里跑，且 `IUserContextGuard` 在进程身份是 SYSTEM 时直接拒绝
  （登录界面 / 锁屏 / UAC 桌面的 Agent 就是 SYSTEM）。所以锁屏状态下连上来的人不能借机读整块磁盘。
- **文件路径**：必须是绝对路径，拒绝设备路径（`\\.\`、`\\?\`）、NTFS 备用数据流、`CON`/`NUL` 等保留名，
  `..` 先解析再判断是否越出允许的根目录。没传根目录时，能访问的就是登录用户自己有权访问的东西。
- **文件完整性**：目标文件夹里出现完整文件之前，内容一直写在 `<目标名>.<大小>-<修改时间>.rdpart` 里，
  校验（xxHash64）通过才改名，所以目标名下不会出现写了一半的文件。
- **残片不会永远留着**：被控端把残片记在一份清单里，超过 7 天没人续传的会被删除（`PartialFileSweeper`）。
  没有这一步，一个反复开始又放弃传输的控制端可以不断在某人的文件夹里留下文件——每个的大小都不一样，
  所以每个都是新名字。正在写入的残片有最新的修改时间，不会被碰。
- **终端**：控制端不能指定程序路径，只能选被控端列出的名字；shell 和它启动的子进程放在作业对象里，
  关标签、断连接、Agent 退出都会一起结束。终端**不记录键入内容**（只记录打开/退出/关闭）。
- **终端里的剪贴板**：控制端的复制粘贴是本地行为；被控端程序发来的 OSC 52（让终端写系统剪贴板）被刻意忽略，
  否则被控端上的程序就能写控制端的剪贴板。
- **审计**：文件的新建/重命名/删除/上传/下载、终端的打开/退出、摄像头的打开/关闭都写进 Agent 日志，带真实会话 ID；
  不记录文件内容，也不记录终端输入。

## 本机的进程边界

- **后台服务**（LocalSystem）只做网络、鉴权、授权和转发——它不采集屏幕、不注入输入、不碰文件。真正干活的 Agent
  在交互会话里以**登录用户**运行；只有登录界面 / UAC 时服务才换成 SYSTEM 令牌的 Agent，而那时上表的功能全部拒绝。
- **UIPI 突破机制 (UIAccess)**：为了能够远程操作“任务管理器”或管理员权限的窗口而不被系统卡住鼠标，`SessionAgent` 开启了 `uiAccess="true"`。这意味着该 Agent 必须具有合法的代码签名并安装在安全的系统目录 (Program Files) 中，由 SYSTEM 权限的 HostService 拉起。
- **服务 ↔ Agent 命名管道**：ACL 只允许启动 Agent 的那个用户，并且校验连接方的进程 ID 就是它启动的进程。
- **界面 ↔ 服务控制管道**：ACL 允许本机已认证用户（界面是普通用户进程）。这条管道的命令是读状态、刷新临时密码、
  把某个会话降级为仅观看、断开某个会话、开关摄像头同意。

## 部署者必须自己做的事

1. **生产环境必须换掉中继共享密钥**（`RelaySharedKey`）。仓库里的开发配置带的是开发用密钥；这个密钥用来签发中继票据，
   泄露的话别人可以白用你的中继带宽。
2. **信令必须放在 TLS 后面**（`wss://`），做法见 [deployment.md](deployment.md) 的"生产环境：信令必须走 TLS"
   （服务器自带证书，或前面放反向代理并配 `TrustedProxies`）。**这不是可选项**：不加密时，信令里的中继票据
   在途可被拿走抢用，而下面的 PAKE 那条也会跟着变得更容易利用。
   它能看到设备代码、IP、连接时间等元数据（看不到画面和按键内容）。
   它属于可用性和元数据层面的信任面，不是内容层面的。
   **在线状态查询**让这个面变宽了一点：客户端可以问服务器"这些设备代码现在在线吗"，而**被问到的设备不会知道**。
   在这之前，想知道一台设备在不在线只能去连它，对方会看到连接请求。代价是：服务器（或被劫持的服务器）按定时器
   就能拿到这台机器的整份最近设备列表，并且两个方向都能撒谎——谎报在线只会让人白试一次（连接仍要过密码证明、
   指纹固定和 QUIC 握手），谎报离线是软性拒绝服务，也正是状态灯不禁用任何按钮的原因。按设备的令牌桶只能收窄
   批量抓取，**消除不了这个暴露面**，所以它是文档里的一条而不是一个协议技巧。不需要这个功能的部署把
   `Rendezvous:PresenceEnabled` 设为 `false`：行为与旧版服务端完全一致，客户端显示"未知"。
3. **安装包要签名**：`build-installer.ps1` 会自动找本机可用的代码签名证书（名字与本产品相符才自动选），也可以用
   `-SignCertificate <指纹或 CN>` 指定；不签名时 SmartScreen 和企业策略可能拦住安装。
4. **不要随便开固定密码**：固定密码适合无人值守（由 DPAPI 强加密存储），它是长期有效的第二把钥匙；临时密码更适合有人值守的临时协助场景。
   下限 6 位由服务端强制（不只是在界面上检查），但**6 位只是下限不是建议**——参见下面 PAKE 那一条，口令是这套设计里最薄的一环，
   能设多长就设多长。
5. **排查问题时注意日志里有文件路径**（不含内容）。

## 还没有做的事（按重要程度）

- **密码证明不是 PAKE**：`PasswordProof` 是一段挑战—应答，不是 PAKE（`PasswordProof.cs` 里写明了这一点）。
  任何能**以被控端身份完成 TLS 握手**的一方——被劫持或恶意的信令服务器，或在信令没有加密时任何在路径上的
  攻击者——都能拿到一份可离线验证的证明，然后在自己机器上穷举口令。
  **已经做的**：口令先经 60 万轮 PBKDF2 才成为密钥（双方每次连接都要付这份计算，所以配合失败限流，
  它不构成新的拒绝服务面），盐是每次连接新生的 nonce。这让每一次猜测都贵了约六个数量级。
  **没有做的**：把整个攻击从"离线可爆破"变成"不可爆破"。口令熵不够时，加价只是拖延，不是阻止——
  临时密码 12 位 33 种字符约 2^60（8 位只有 2^40，那是租来的 GPU 农场几天的事，所以加长了），
  固定密码最短 6 位且由人自选——**真正需要 PAKE 的是固定密码**：人挑的口令熵本来就低，加价救不了它。
  计划仍是换成 SPAKE2 或 OPAQUE，
  那需要选一个经过审阅的实现或引入一个成熟库，不是手写一个 PAKE（手写的 PAKE 比现在这段更危险）。
  **在那之前：信令必须加密，固定密码要足够长，不要把临时密码给不信任的人。**
- **没有账号体系**：只有"设备代码 + 密码"这一个因素，没有二次验证，也没有跨设备的登录审计中心。
- **本机用户之间不做区分**：任何已登录的本机用户都能通过控制管道读到设备代码和临时密码、开关摄像头同意。
  单用户机器上这没问题；多人共用且彼此不信任的机器上，应当把本机用户都视为可信。
  **这是有意留下的，不是没想到**：能真正堵住它的做法是"只允许控制台会话的那个用户"，但那会让**通过 RDP
  登录的管理员自己的客户端界面失效**，而在无头机器上（这个产品的常见用法）根本没有控制台用户，
  于是又退回原样。换句话说，问题不是"怎么实现"，而是"一台机器的设备代码和密码属于谁"——
  这需要产品决定，代码里没有替它做决定。
- **许可文本还是草稿**：`build/installer/License.txt` 是专有 EULA 模板，方括号里的公司名称、联系方式和
  司法管辖区必须换成你自己的正式信息（构建会把它转成安装向导的许可页，改这个文件就够了）。
- **没有 URL 协议**：原设计里的 `remotedesktop://` 一键连接还没实现。
- **卸载不清理用户数据**：MSI 卸载默认保留 `%ProgramData%\RemoteDesktop`（设备身份 + 日志），
  `msiexec /x ... REMOVEDATA=1` 才会删；客户端在 `%AppData%` 下的身份文件 MSI 不管。
- **没有做长时间对抗性测试**：握手洪泛上限、限流窗口这些数字是按常见情况选的，没有在真实攻击流量下压过。
- **没有独立的第三方审计**：上面每一条都能在代码里对上，但都出自同一个实现者视角。

## 怎么验证这些说法

- 单元测试：`AccessGrant`（观看模式、缺屏幕权限）、密码证明与限流、临时密码过期、路径沙盒、终端按键编码、
  握手配额、注册与连接请求的令牌桶、中继绑定令牌。
- 集成测试：真实 QUIC 会话上的权限执行（观看模式拒绝输入/剪贴板/文件/终端/摄像头）、SYSTEM 身份拒绝、
  摄像头同意与收回、会话隔离、**信令走 TLS**（含"不受信任的证书会被拒"）、连接配额与注册限流、
  中继两步绑定、`/health` 反映数据库。
- 真机验证记录见 README 的里程碑部分。
- **仍然没有第三方审阅**：上面每一条都能在代码里对上，也都由测试盯着，但盯着的还是同一个人写的那套假设。
