# 文档规范

这份文档规定**文档放哪、叫什么、怎么写、什么时候更新**。它的定位和 `CONTRIBUTING.md` 一样：不是建议清单，
而是这个仓库的约定——新文档和改动现有文档时都按它来。

和 `CONTRIBUTING.md` 的分工：那份管**代码**，这份管**文档**。两者都指向同一件事——让下一个人不用问就能找对地方。

> **为什么要有这份文件。** 在此之前，文档约定散在三处：`CONTRIBUTING.md` 讲了一点、`build/README.md` 讲了一点、
> `docs/README.md` 又讲了一点。三轮目录结构评审每轮都能挑出新的不一致（索引漏项、命名混乱、评审被当成现行约定），
> 因为"写在哪"本身就是分散的。现在收成一份，并且**其中能机器判断的部分已经变成测试**（见 §7）。

## 1. 文档分两类，生命周期不同

这是最重要的一条。写文档前先回答：**它属于哪一类？** 两类文件在"会不会更新"上是相反的，混用会直接误导读者。

| 类别 | 回答什么问题 | 会更新吗 | 放在哪 |
|---|---|---|---|
| **规范 / 指南**（living） | "现在应该怎么做"；已完成事项的**结论**也算这一类（如 `docs/ports/`，两个移植都已完成，它记的是定下了什么、没验证什么） | **会**，与代码同步改动 | `docs/usage/`、`docs/design/`、`docs/ops/`、`docs/ports/`、根目录 |
| **计划**（plan） | "还要做什么"：阶段、风险、未验证项 | **会**，随进展更新 | 与主题同级的目录（目前没有进行中的计划文档） |

判断一个文件属于哪类，看有没有 `-plan` 后缀即可（命名规则见 §3）。

## 2. 放哪：按读者分目录

`docs/` 下的第一层是**读者**，不是主题：

| 目录 | 给谁看 | 装什么 |
|---|---|---|
| `docs/usage/` | 用这个软件的人 | 支持矩阵、功能说明、平台限制 |
| `docs/design/` | 要改代码的人 | 分层与模块、通信协议、安全边界 |
| `docs/ops/` | 要部署和运维的人 | 架服务器、发版、安装、打包、排错 |
| `docs/ports/` | 要把产品搬到某个平台的人 | 各平台移植的决策、硬约束、未验证项 |
| `docs/` 根 | 索引与规则本身 | 本文件与 `README.md` |

`docs/` 根**只放两样东西**：文档索引 `README.md` 和本文件。其余一律进子目录——根目录一旦开始长文件，
"这里什么都有"就会让读者不再往下看。

**一个目录装一份完整的文档，它就是那个目录的 `README.md`。** 读者按目录名找到东西，打开就是全文——
不要把一个主题拆成三份让读者猜该看哪一份，也不要在目录里放一组零散的补充材料。

`build/` 与 `native/` 下的 `README.md` 是同一类东西，同样遵守本规范。

## 3. 叫什么：文件名规范

一律**小写 kebab-case**。不用 CamelCase、不用下划线、不用中文。
理由很实际：跨平台、大小写不敏感的机器上不会撞名，URL 里也不用转义。

两个名字例外，因为它们是**约定**而不是决定：`README.md`（每个目录的主文档与入口，见 §2）与
`STYLE.md`（本文件）。仓库根与 `.github/` 下的文件名由 GitHub 固定（`CONTRIBUTING.md`、
`PULL_REQUEST_TEMPLATE.md`），也照它的来。

后缀有含义，只有这一个：

| 后缀 | 含义 | 例子 |
|---|---|---|
| `-plan` | 还要做的事（计划类） | 计划完成后并入主题目录的 `README.md`（先例：两份移植计划、运维监控台） |

其余没有后缀。

文档目录名同样是 kebab-case。（代码项目的目录名 == 里面的 `.csproj` 名是另一条规则，写在 `CONTRIBUTING.md`，
由 `RepositoryStructureTests` 在 `src/` 与 `tests/` 下断言。）

## 4. 必备文件

下面这些文件是仓库对外约定的入口，缺一个就会有链接指向空白：

| 文件 | 作用 | 谁在读它 |
|---|---|---|
| `README.md` | 落地页：这是什么、怎么跑起来、去哪看细节 | 所有人，包括第一次来的人 |
| `CONTRIBUTING.md` | 代码怎么提交、环境、依赖规则 | 贡献者 |
| `SECURITY.md` | 漏洞怎么上报 | GitHub 安全页、安全研究者 |
| `CHANGELOG.md` | 版本变更（[Keep a Changelog](https://keepachangelog.com/zh-CN/1.0.0/)） | 使用者、发布者 |
| `LICENSE` | 许可条款 | 法务、使用者 |
| `docs/README.md` | 文档索引 | 想找文档的人 |
| `docs/*/README.md` | 四份读者主文档（使用 / 设计 / 运维 / 移植），见 §2 | 各自那一类读者 |
| `docs/STYLE.md` | 本文件 | 写文档的人 |
| `.github/PULL_REQUEST_TEMPLATE.md` | PR 要回答的问题 | 提交 PR 的人 |

`THIRD-PARTY-NOTICES.md` 是**生成物**（`build/tools/Export-ThirdPartyNotices.ps1`），不要手改——手改会被 CI 打回。

## 5. 怎么写：README 是落地页，不是手册

README 的职责是**让人在三十秒内知道这是什么、怎么跑起来、然后去哪里看细节**。它不承担手册的职责。

这意味着：

- 功能细节（文件传输怎么用、终端支持什么、摄像头怎么授权）**不在 README**，在 `docs/` 里，README 只给一行摘要和链接。
- 反过来，README 里出现任何一段只能靠"往上翻"才能看懂的正文，就是该下沉的信号——**下沉不是删掉，是搬到
  `docs/` 并在 README 留一个链接**。
- README 必须有的章节：**构建与测试**、**文档**（导航）、**许可证**。这三节是外部读者最先找的东西。

其他通用写作规则：

- **一个文件一个 H1**，就是标题；且它必须是文件的第一行。层级不要跳（`##` 下面直接 `####` 是错的）。
- **代码块必须标语言**（` ```bash `、` ```text `），否则 CI 会拦（见 §7）。
- **链接用相对路径**，且必须真的存在。指向另一个文档的正文引用写成 `[标题](相对路径.md)`，不要写成行内代码
  ——行内代码的路径不会被检查，会静默腐烂。
- **代码注释引用文档时按小节名引**（`见 docs/ports/README.md 的"……"一节`），不写 `§3.4` 这类编号——
  文档重排后编号必烂。注意这条路**没有任何测试兜底**（链接检查只扫 `.md`），所以被引用的小节改名时，
  要全仓搜一遍 `.cs` / `.sh` / `.yml` 的注释（见 §8 检查清单）。
- **中文正文里用中文标点**；英文缩写、代码标识符、路径保持原样。产品名按 `CONTRIBUTING.md` 的拼写规矩
  （路径全小写、C# 标识符 PascalCase、散文写 Apple 的 `macOS`）。
- 表格用来做对照（A 平台 vs B 平台），不要用来塞长段落。
- 命令一律给完整、可直接粘贴的形式；有前提（管理员、需要装的东西）就写在命令上面一行。

## 6. 计划类文档的写法

`-plan` 文件是**活的**，但活的方式和规范类不同——它记录"没做完的"：

- 每个阶段明确标**已完成 / 进行中 / 明确不做**，不要留模糊的"待定"。
- **未验证的东西要说出来**。这个仓库里有很多"代码写了但没在真机上跑过"的项（比如 Linux 摄像头），
  计划文档必须把这些标成未验证而不是写成已实现——这类"假完成"是文档最容易犯、代价最高的错误。
- 实测结论（在某台机器上看到什么）写进计划文档，不要只留在提交信息里。

## 7. 靠测试，不靠自觉

写下来的规则会腐烂，除非有人在你违反时报错。本仓库的态度和 `CONTRIBUTING.md` §仓库结构规则 一致：
**能机器判断的，就变成断言或 CI 作业。**

| 规则 | 谁来管 | 在哪 | 违反时 |
|---|---|---|---|
| 必备文件存在（§4） | `DocumentationTests` | `dotnet test` | 构建红 |
| 一个文件一个 H1（§5） | `DocumentationTests` | 同上 | 构建红 |
| `docs/` 下每个文档都被索引（§2） | `DocumentationTests` | 同上 | 构建红 |
| 相对链接可解析（§5） | `DocumentationTests` | 同上 | 构建红 |
| 文件名规范（§3） | `DocumentationTests` | 同上 | 构建红 |
| README 必备章节（§5） | `DocumentationTests` | 同上 | 构建红 |
| 代码块标语言、列表/标题空行等**格式** | [markdownlint](https://github.com/DavidAnson/markdownlint) | CI 的 `docs` 作业 | PR 红 |
| 文档与代码一致（"现在怎么做"） | 人 | review | —— |

测试文件是 `tests/RemoteDesktop.Architecture.UnitTests/DocumentationTests.cs`。
**它与本文档冲突时以测试为准**——改成文档容易，改漏测试也容易，所以两者不一致时先怀疑文档。

分工的理由：`DocumentationTests` 管**语义**（这个文件该不该存在、名字对不对、链接通向哪里），
markdownlint 管**格式**（空行、缩进、代码块标注）。前者需要读仓库结构，后者是纯文本规则，各用各自擅长的工具。

例外一律**列出来**，不静默跳过。列表的意图是缩短到消失。

## 8. 改文档时的检查清单

提交前过一遍：

1. 这个文件属于哪一类？`-plan` 后缀对了吗？（§1、§3）
2. 放在对的目录里吗？（§2）
3. 新文件加进 `docs/README.md` 索引了吗？（漏了 `DocumentationTests` 会拦）
4. 移动或改名了文件？**全仓搜一遍旧路径**——引用散在 `.md`、`.cs` 注释、`.yml`、`.sh`、`.ps1` 里，不只 Markdown。
5. 改了被代码注释引用的小节名？同样全仓搜——`.cs` / `.sh` / `.yml` 注释里的小节名引用没有任何测试兜底（§5）。
6. 改了链接？`dotnet test` 里那条链接检查跑过了吗？

## 9. 加一份新文档

```text
# 1. 决定类别与目录（§1、§2），选好名字（§3）
# 2. 写正文：一个 H1、代码块标语言、相对链接（§5）
# 3. 把它加进索引
$EDITOR docs/README.md
# 4. 本地验证：结构、命名、链接
dotnet test tests/RemoteDesktop.Architecture.UnitTests
# 5. 格式（若本地装了 node）
npx --yes markdownlint-cli2@0.23.3 "**/*.md"
```

第 4 步是必须的——它会替你检查本文档里 §7 那张表的上半部分。
